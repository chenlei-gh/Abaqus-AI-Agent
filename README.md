# Abaqus AI Agent\n\nOpen-source engineering agent for Abaqus/CAE.\n\n## Goal\n\nexperiment requirements + material data + existing Abaqus model + annotated image -> engineering intent -> geometry grounding -> validated native Abaqus actions -> job -> ODB evidence.\n\nThe project separates intent, grounding, action, execution, and evidence.\n\n## Implemented capability\n\n### Live Abaqus execution\n\n- AbaqusExecutor abstraction.\n- JSON/TCP BridgeExecutor for the common local live-Abaqus bridge pattern.\n- InProcessExecutor for tests.\n- model inspection, job submission/status, ODB inspection and viewport capture helpers.\n- arbitrary native Abaqus Python through python_action, so typed builders do not become an artificial ceiling on Abaqus functionality.\n\n### Engineering actions\n\n- material elasticity, density and plasticity;\n- solid sections and section assignment;\n- static, explicit-dynamic and frequency steps;\n- fixed, displacement and symmetry BCs;\n- pressure, concentrated-force and body-force loads;\n- field/history output;\n- mesh seeding and mesh generation;\n- element-type intent;\n- tie/contact intent;\n- job creation and submission.\n\nThe native Python escape hatch covers the long tail of Abaqus APIs without requiring this project to reimplement every release-specific feature.\n\n### Geometry grounding\n\n- normalized image/intent contracts;\n- Face/Edge descriptors from live Abaqus;\n- viewport camera/projection extraction;\n- parallel-projection screen grounding;\n- candidate scoring/ranking;\n- confirmation policy;\n- JSON-safe evidence serialization;\n- read-only viewport PNG probe.\n\nImportant: the agent does not treat Face[17] as evidence that an image annotation means Face 17. A region must be grounded from viewport/image evidence or explicitly supplied by the user.\n\n### Planning / validation / evidence\n\n- experiment input contract;\n- engineering plan with blockers/assumptions;\n- action validation before execution;\n- static-analysis plan builder;\n- job-status classification;\n- ODB metadata normalization;\n- orchestration facade AbaqusAIAgent.\n\n## Architecture\n\nUser -> requirements/material/existing model/annotated image -> intent/planning -> geometry grounding -> validated action -> AbaqusExecutor -> live Abaqus/CAE -> job/ODB evidence -> AI interpretation.\n\n## Reference architecture\n\nThe live-execution boundary follows public Abaqus MCP projects such as Abaqus-Control-MCP and CAE-Agent-Hub: a local bridge exposes live Abaqus/CAE, while reusable skills/actions describe the engineering workflow. Those projects expose arbitrary Python execution, model inspection, job monitoring, ODB inspection and viewport capture. This repository adds geometry-grounding and explicit action/evidence boundaries rather than replacing Abaqus's native API.\n\n## Compatibility\n\nThe external package targets Python 3.9+. Abaqus-side snippets intentionally avoid modern Python-only syntax because Abaqus releases may ship legacy Python runtimes. Exact API compatibility must still be validated against the installed Abaqus release.\n\n## Safety boundary\n\n- no automatic mutation from an ungrounded image coordinate;\n- no invented geometry evidence;\n- no claim that a successful Python call means a successful solver run;\n- job completion and ODB availability are separate evidence;\n- model-specific contact, mesh and release-specific APIs can be supplied through explicit native Python actions.\n\n## Current known limitation\n\nThe remaining hard problem is fully automatic Vision -> Abaqus geometry grounding, especially for arbitrary external photographs rather than screenshots produced by the Abaqus viewport. The current projection path supports calibrated parallel viewport geometry; perspective and uncontrolled external-photo registration are intentionally not claimed yet.\n\n## License\n\nApache-2.0.

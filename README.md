# Abaqus AI Agent\n\nOpen-source engineering agent for Abaqus/CAE.\n\n## Goal\n\nexperiment requirements + material data + existing Abaqus model + annotated image -> engineering intent -> geometry grounding -> validated native Abaqus actions -> job -> ODB evidence.\n\nThe project separates intent, grounding, action, execution, and evidence.\n\n## Implemented capability\n\n### Live Abaqus execution\n\n- AbaqusExecutor abstraction.\n- JSON/TCP BridgeExecutor for the common local live-Abaqus bridge pattern.\n- InProcessExecutor for tests.\n- model inspection, job submission/status, ODB inspection and viewport capture helpers.\n- arbitrary native Abaqus Python through python_action, so typed builders do not become an artificial ceiling on Abaqus functionality.\n\n### Engineering actions\n\n- material elasticity, density, plasticity, conductivity, specific heat and thermal expansion;\n- solid sections and section assignment;\n- static, explicit-dynamic, implicit-dynamic, frequency, heat-transfer and coupled temperature-displacement steps with core increment/stabilization controls;
- tabular, smooth-step, periodic and equally-spaced amplitudes;
- gravity loads and initial temperature/stress predefined fields;
- assembly instance inspection, translation, rotation and linear patterns;
- INP export and ODB field CSV export;
- contract-only fatigue workflow for existing Abaqus stress histories;\n- fixed, displacement, symmetry and temperature BCs;\n- pressure, concentrated-force, body-force, body-heat-flux and surface-heat-flux loads;\n- criterion-driven field, history and frame-value result extraction;\n- mesh seeding and mesh generation;\n- element-type intent;\n- tie/contact intent;\n- job creation and submission;\n- job artifacts and bounded solver diagnostics (.inp/.odb/.sta/.msg/.dat/.log/.cae);\n- session health and runtime capability reporting;\n- batch `.inp`, `cae noGUI` and Abaqus Python execution;\n- mesh convergence evaluation.\n\nThe native Python escape hatch covers the long tail of Abaqus APIs without requiring this project to reimplement every release-specific feature.\n\n### Geometry grounding\n\n- normalized image/intent contracts;\n- Face/Edge descriptors from live Abaqus;\n- viewport camera/projection extraction;\n- parallel-projection screen grounding;\n- candidate scoring/ranking;\n- confirmation policy;\n- JSON-safe evidence serialization;\n- read-only viewport PNG probe.\n\nImportant: the agent does not treat Face[17] as evidence that an image annotation means Face 17. A region must be grounded from viewport/image evidence or explicitly supplied by the user.\n\n### Planning / validation / evidence\n\n- experiment input contract;\n- engineering plan with blockers/assumptions;\n- action validation before execution;\n- static-analysis plan builder;\n- job-status classification;\n- ODB metadata normalization;\n- orchestration facade AbaqusAIAgent.\n\n## Architecture\n\nUser -> requirements/material/existing model/annotated image -> EngineeringIntent -> AnalysisWorkflow -> ModelSnapshot/Viewport/SessionHealth -> geometry grounding -> validated action -> Preflight -> execute -> StateDiff/Error diagnosis -> AnalysisRun -> Job -> artifacts/diagnostics -> ODB -> ResultRequirement -> field/history/frame extraction -> Acceptance -> Evidence.\n\n## Engineering closure\n\nThe critical path is intentionally closed: acceptance criteria are converted into deterministic result requirements, result requirements identify required Abaqus outputs, the completed job is checked through artifacts and ODB metadata, results are extracted with a field/history/frame locator, and only then are acceptance criteria evaluated. Solver completion alone is never treated as engineering acceptance.\n\n## Reference architecture\n\nThe live-execution boundary follows public Abaqus MCP projects such as Abaqus-Control-MCP and CAE-Agent-Hub: a local bridge exposes live Abaqus/CAE, while reusable skills/actions describe the engineering workflow. Those projects expose arbitrary Python execution, model inspection, job monitoring, ODB inspection and viewport capture. This repository adds geometry-grounding and explicit action/evidence boundaries rather than replacing Abaqus's native API.\n\n## Compatibility\n\nThe external package targets Python 3.9+. Abaqus-side snippets intentionally avoid modern Python-only syntax because Abaqus releases may ship legacy Python runtimes. Exact API compatibility must still be validated against the installed Abaqus release.\n\n## Safety boundary\n\n- no automatic mutation from an ungrounded image coordinate;\n- no invented geometry evidence;\n- no claim that a successful Python call means a successful solver run;\n- job completion and ODB availability are separate evidence;\n- model-specific contact, mesh and release-specific APIs can be supplied through explicit native Python actions.\n\n## Current known limitation\n\nThe remaining hard problem is fully automatic Vision -> Abaqus geometry grounding, especially for arbitrary external photographs rather than screenshots produced by the Abaqus viewport. The current projection path supports calibrated parallel viewport geometry; perspective and uncontrolled external-photo registration are intentionally not claimed yet.\n\n## License\n\nApache-2.0.
